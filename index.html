Git 是什麼？

Git 是一個分散式版本控制系統（Distributed Version Control System），由 Linus Torvalds 於 2005 年開發， 用於追蹤程式碼的變更、協調多人開發，並讓開發者可以隨時回溯到任何歷史版本。

🔄

版本追蹤

記錄每一次程式碼的變更，隨時可以查看歷史紀錄或回到任何版本。

👥

多人協作

支援多人同時開發，透過分支與合併機制，讓團隊協作更有效率。

🔒

分散式架構

每個開發者都有完整的本地倉庫，即使伺服器掛掉也能繼續開發。

🔗

分支管理

輕鬆建立、切換、合併分支，支援各種開發流程（如 Git Flow、GitHub Flow）。

核心概念

概念 說明
Repository（倉庫） 存放專案所有檔案與版本歷史的地方，分為本地（Local）與遠端（Remote）。
Commit（提交） 一次程式碼變更的快照，包含變更內容、作者、時間與訊息。
Branch（分支） 獨立的開發線，讓你可以平行開發不同功能而不互相干擾。
Merge（合併） 將一個分支的變更整合到另一個分支。
Remote（遠端） 遠端伺服器上的倉庫，如 GitHub、GitLab、Bitbucket 等。
Working Directory（工作目錄） 你目前正在編輯的檔案所在目錄。
Staging Area（暫存區） 準備要提交的檔案暫存區域，又稱 Index。

Git 的三個區域

Working Directory
工作目錄 ➔ Staging Area
暫存區 ➔ Repository
本地倉庫

git add 將檔案加入暫存區  |  git commit 將暫存區內容提交到倉庫

安裝與設定

安裝 Git

作業系統 安裝方式
Windows 下載 Git for Windows 安裝檔，或使用 winget install Git.Git
macOS 使用 Homebrew：brew install git，或安裝 Xcode Command Line Tools
Linux (Ubuntu/Debian) sudo apt install git
Linux (CentOS/RHEL) sudo yum install git

驗證安裝

git --version
# 輸出範例：git version 2.43.0

初次設定

安裝完成後，需要設定你的使用者名稱與 Email，這些資訊會記錄在每次的 Commit 中。

git config --global user.name "你的名字"
git config --global user.email "你的email@example.com"

# 查看目前的設定
git config --list

# 設定預設分支名稱為 main（Git 2.28+）
git config --global init.defaultBranch main

💡 小提示

使用 --global 表示對所有專案生效；如果只想對目前專案設定，可以省略 --global。 也可以使用 --local 明確指定只對目前專案生效。

基礎操作

建立新倉庫

git init
# 在目前目錄初始化一個新的 Git 倉庫

檢查狀態

git status
# 查看目前工作目錄的狀態

暫存與提交

# 將檔案加入暫存區
git add index.html # 加入單一檔案
git add . # 加入所有變更
git add src/ # 加入整個目錄

# 提交變更
git commit -m "新增首頁"

# 暫存並提交（跳過 git add）
git commit -am "更新 README"

⚠️ 注意

git commit -am 只會暫存已追蹤（已加入過）的檔案變更， 新建立的檔案仍需先使用 git add。

查看提交歷史

git log
# 查看完整的提交歷史

git log --oneline
# 簡潔的單行顯示

git log --oneline --graph --all
# 以圖形方式顯示所有分支的歷史

git log -p
# 顯示每次提交的詳細變更內容

查看變更內容

git diff
# 查看工作目錄與暫存區的差異

git diff --staged
# 查看暫存區與上次提交的差異

git diff HEAD
# 查看工作目錄與上次提交的差異

.gitignore 檔案

.gitignore 用來指定哪些檔案或目錄不應該被 Git 追蹤， 例如：編譯產物、依賴套件、環境設定檔等。

# .gitignore 範例
# 忽略 node_modules 目錄
node_modules/

# 忽略所有 .log 檔案
*.log

# 忽略環境設定檔
.env
.env.local

# 忽略建置產物
dist/
build/

💡 實用技巧

可以使用 git check-ignore -v 檔案名稱 來檢查某個檔案是否被 .gitignore 忽略， 以及是哪一條規則造成的。

分支管理

分支是 Git 最強大的功能之一。它讓你可以獨立開發新功能、修復 Bug， 而不會影響主分支（通常是 main 或 master）的穩定性。

分支的基本操作

# 查看所有分支（* 表示目前所在分支）
git branch

# 建立新分支
git branch feature/login

# 切換到指定分支
git checkout feature/login

# 建立並切換到新分支（最常用）
git checkout -b feature/login
# 或使用較新的語法
git switch -c feature/login

# 刪除分支
git branch -d feature/login

# 強制刪除未合併的分支
git branch -D feature/login

分支視覺化

main ●──●──●────────────● (合併點)
│ │
feature └──●──●──● (新功能開發)

合併分支

有兩種主要的合併方式：Merge 和 Rebase。

1. Merge（合併）

# 先切換到目標分支（例如 main）
git checkout main

# 將 feature 分支合併到 main
git merge feature/login

2. Rebase（變基）

# 在 feature 分支上，將 main 的最新變更整合進來
git checkout feature/login
git rebase main

💡 Merge vs Rebase

Merge：保留完整的歷史紀錄，會產生一個合併提交（Merge Commit），適合團隊協作。
Rebase：將分支的提交重新排列到目標分支之上，歷史較乾淨，但會改寫提交歷史，不建議在已推送的公共分支上使用。

解決衝突（Conflict）

當兩個分支修改了同一個檔案的相同位置時，合併會產生衝突。 Git 會在檔案中標記衝突區域，需要手動解決。

# 衝突標記範例
<<<<<<< HEAD
console.log("main 分支的版本");
=======
console.log("feature 分支的版本");
>>>>>>> feature/login

解決衝突的步驟：

  1. 手動編輯檔案，保留想要保留的內容，刪除衝突標記
  2. 使用 git add 將解決後的檔案加入暫存區
  3. 使用 git commit 完成合併
# 解決衝突後
git add index.html
git commit -m "解決衝突：合併登入功能"

遠端協作

遠端倉庫（Remote Repository）是存放在伺服器上的 Git 倉庫， 常見的平台有 GitHub、GitLab、Bitbucket 等。

複製遠端倉庫

git clone https://github.com/使用者名稱/專案名稱.git
# 複製遠端倉庫到本地

git clone https://github.com/使用者名稱/專案名稱.git my-project
# 複製並指定本地目錄名稱

查看遠端倉庫

git remote -v
# 查看遠端倉庫列表

git remote add origin https://github.com/使用者名稱/專案名稱.git
# 新增遠端倉庫（origin 是慣例名稱）

推送與拉取

# 推送本地分支到遠端
git push origin main

# 第一次推送新分支時，加上 -u 建立追蹤關係
git push -u origin feature/login

# 拉取遠端變更並合併到目前分支
git pull

# 只下載遠端變更，不自動合併
git fetch

⚠️ Pull vs Fetch

git pull = git fetch + git merge。 fetch 只會下載遠端變更到本地，不會自動合併； pull 則會直接合併到目前分支。

Pull Request / Merge Request

在團隊協作中，通常不會直接推送變更到 main 分支， 而是透過 Pull Request（PR） 或 Merge Request（MR） 進行程式碼審查。

  1. 從 main 建立一個功能分支
  2. 在功能分支上開發並提交
  3. 推送功能分支到遠端
  4. 在 GitHub/GitLab 上建立 PR/MR
  5. 團隊成員進行程式碼審查
  6. 審查通過後合併到 main

標籤（Tag）

# 建立標籤（通常用於版本發布）
git tag v1.0.0

# 建立附註標籤
git tag -a v1.0.0 -m "正式版 1.0.0"

# 查看所有標籤
git tag

# 推送標籤到遠端
git push origin v1.0.0

撤銷與還原

開發過程中難免會犯錯，Git 提供了多種方式來撤銷或還原變更。

撤銷工作目錄的變更

# 還原工作目錄中未暫存的變更
git checkout -- index.html
# 或使用較新的語法
git restore index.html

# 還原所有未暫存的變更
git restore .

取消暫存

# 將檔案從暫存區移出（保留工作目錄的變更）
git reset HEAD index.html
# 或使用較新的語法
git restore --staged index.html

修改最後一次提交

# 修改最後一次提交的訊息
git commit --amend -m "修正後的提交訊息"

# 將遺漏的檔案加入最後一次提交
git add 遺漏的檔案.js
git commit --amend --no-edit

⚠️ 警告

git commit --amend 會改寫提交歷史。 如果該提交已經推送到遠端，請勿使用此指令，否則會造成團隊成員的困擾。

Reset（重設）

# Soft Reset：只移動 HEAD，保留暫存區與工作目錄
git reset --soft HEAD~1

# Mixed Reset（預設）：移動 HEAD 並取消暫存，保留工作目錄
git reset HEAD~1

# Hard Reset：完全丟棄變更（危險！）
git reset --hard HEAD~1

⚠️ 危險操作

git reset --hard 會永久刪除工作目錄中的未提交變更， 且無法復原。使用前請務必確認。

Revert（還原提交）

# 建立一個新的提交來還原指定的提交
git revert abc1234

# 還原多個提交
git revert abc1234..def5678

💡 Reset vs Revert

Reset：移動 HEAD 指標，改寫歷史，適合尚未推送的提交。
Revert：建立新的提交來抵消舊提交，保留歷史，適合已推送的提交。

找回遺失的提交

# 查看所有分支的提交（包含已刪除的）
git reflog

# 使用 reflog 找到的 hash 恢復分支
git checkout -b recovered-branch abc1234

暫存 Stash

當你正在開發某個功能，但需要緊急切換分支處理其他事情時， 可以使用 git stash 將目前的變更暫時保存起來。

基本操作

# 暫存目前的變更（包含已追蹤的檔案）
git stash

# 暫存所有變更（包含未追蹤的檔案）
git stash -u

# 查看暫存列表
git stash list

# 恢復最近一次的暫存（並從列表中移除）
git stash pop

# 恢復暫存（但保留在列表中）
git stash apply

# 刪除暫存
git stash drop

進階操作

# 為暫存加上說明
git stash push -m "登入功能開發中"

# 查看暫存的詳細內容
git stash show -p stash@{0}

# 從暫存建立新分支
git stash branch feature/stash-recovery

💡 實用情境

假設你在 feature/login 分支開發到一半，突然發現 main 有緊急 Bug 要修。 你可以 git stash 保存進度 → 切到 main 修 Bug → 再切回來 → git stash pop 恢復進度。

常見工作流程

Git Flow

Git Flow 是較嚴謹的分支管理策略，適合需要定期發布的專案。 主要分支包含：main（正式版）、develop（開發版）、 feature/*（功能）、release/*（發布）、hotfix/*（緊急修復）。

main ●──────────────────────────────●──●
│ │ │
release └──●──●──●──────────────│ │
│ │ │
develop └──●──●──●──●──●──●──●──│
│ │
feature └──●──●──● │
│
hotfix └──●──●

GitHub Flow

GitHub Flow 是較輕量的工作流程，適合持續部署的專案。 只有一個主要分支 main，所有開發都透過功能分支 + Pull Request 進行。

  1. 從 main 建立功能分支
  2. 在功能分支上進行開發與提交
  3. 推送分支並建立 Pull Request
  4. 討論與程式碼審查
  5. 合併到 main 並部署

Trunk-Based Development

所有開發者直接在 main（或 trunk）上開發， 使用短命的功能分支或直接提交。適合 CI/CD 成熟、測試覆蓋率高的團隊。

💡 選擇建議

小型團隊 / 新專案：建議使用 GitHub Flow，簡單且彈性高。
大型團隊 / 定期發布：建議使用 Git Flow，結構嚴謹。
DevOps 成熟團隊：可考慮 Trunk-Based Development。

最佳實踐

Commit 訊息規範

良好的 Commit 訊息能讓團隊更容易理解變更內容。常見的規範如下：

# 使用 Conventional Commits 規範
feat: 新增使用者登入功能
fix: 修正登入頁面載入過慢的問題
docs: 更新 API 文件
style: 調整程式碼排版
refactor: 重構認證模組
test: 新增登入功能的測試案例
chore: 更新相依套件

Commit 原則

  • 小而專注：每個 Commit 只做一件事，方便追蹤與回滾
  • 頻繁提交：完成一個小任務就提交，不要累積大量變更
  • 不要提交敏感資訊：密碼、API Key 等絕對不能提交
  • 不要提交建置產物：使用 .gitignore 排除
  • 提交前先檢查：使用 git diff 確認變更內容

分支命名規範

類型 命名範例
功能 feature/login、feature/user-profile
修復 fix/button-alignment、bugfix/api-timeout
緊急修復 hotfix/security-patch
發布 release/v1.2.0
重構 refactor/auth-module
測試 test/unit-tests

團隊協作建議

  • 每天開始工作前先 git pull 取得最新變更
  • 推送前先 git pull --rebase 避免產生不必要的合併提交
  • 使用 Pull Request 進行程式碼審查
  • 設定分支保護規則，禁止直接推送到 main
  • 使用 CI/CD 自動化測試與部署
